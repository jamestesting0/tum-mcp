# Practice that tests a useful decision

Start with the reasoning demand, then solve the item independently before writing
options. Check the shortest valid solution against the objective. If it bypasses a
named action, revise the question or narrow the objective. Choosing the next queue
entry does not test recovering a path from parents. An already supplied eigenvector
can let a student compute the action of an exponential without diagonalizing a matrix.
Add an item for a distinct objective, misconception or transfer demand. Remove
paraphrases that test the same decision. No fixed bank size or difficulty quota.

Choose the demand that fits the goal:

| Demand | Evidence it can provide |
| --- | --- |
| Recall | Retrieve a condition, definition or invariant before reveal |
| Discrimination | Choose between plausible methods using the actual constraints |
| Composition | Combine familiar inferences without a step naming each method |
| Reverse or premise | Infer a missing input or explain which assumption a claim needs |
| Changed case | Adapt reasoning when a meaningful condition or representation changes |

Ask only what the lesson teaches: every term, rule and fact a card or question needs
appears in the lesson's blocks first. A card whose answer lives only in the source
teaches the source, not the lesson; add the idea to the lesson or drop the card.

Do not count replay of a worked input and answer as application evidence. A new input
that requires the student to calculate or decide is valid routine application. A deeper
transfer demand needs a consequential change in conditions, representation or decision;
cosmetic renaming alone does not establish it. Choose the demand the objective needs,
without requiring every beginner question to be a transfer problem.
A useful progression might pair a trace with a choice of method and a changed
assumption. Keep only the members that teach or test different decisions.

Use the checked plan's `practice` contrasts and solved answers. Before submitting the
draft, compare each application question with the actual worked blocks: could a student
answer by remembering their final state or copying worked intermediate states unchanged? If yes,
change the condition or decision and solve again. Check that the shortest valid solution
still needs the intended learning, and that all prerequisites are taught. A new graph
alone does not prove transfer; a familiar graph with a consequentially changed condition
may test it well. Keep this check in the author's existing polish pass.

Reserve the planned assessment cases while writing the lesson. Do not turn their inputs
or solved answers into worked examples, including untitled continuations and variants.
If teaching consumes a reserved case, replace and solve the assessment case. Check that
the claimed contrast remains true of the finished lesson. Compare against actual solved
inputs and answers, not general rules: teaching a tie rule does not solve every future
tie problem. Shared numbers or a familiar graph are not defects by themselves when the
student must derive a new result or eligible set. Retain useful routine application and
add substantive transfer where the objective calls for it. Do not invent a new prerequisite
merely to make a question different.

Every question must stand alone in both topic Practice and pooled Revision. When it is
about a situation, show that situation in the question's `blocks` (the graph with its
weights, the drawn setup, the table, the formula, the code) and let the prompt ask only
the question; say each fact once. Systems or cases to classify are a table the student
scans. Every question has a code snippet, diagram, formula, table or plot carrying
information it needs, including conceptual questions. If the context would be a
decorative picture or a table repeating the prompt, write a richer case that makes
the concept useful instead. `text_only_question` holds the gate; brevity is not an
exemption. Include
notation, units and assumptions the answer depends on. A reference to “the graph above” breaks when the
item is pooled. An optional `hint` recalls the idea without naming the option.

Write the stem as one question a student could answer with the options covered. A
context table has headers naming what it carries, never generic ones such as "Feature" or
"Information" (`generic_table`). Avoid negative stems; when one is unavoidable, set NOT
or EXCEPT in capitals (`negative_stem`).

Write four distinct options by default; the schema sets the accepted range. Map
each distractor to a plausible reasoning error, and verify every option under the
stated assumptions. Revise ambiguous premises; never force a key. The app shows options
in a stable shuffled order. Match option length and grammar: a key much longer than the
others (`key_longest`) or the only option repeating a stem word (`stem_key_overlap`)
gives itself away. No joke options and no "all/none of the above" (`all_of_above`). If
no further meaningful option exists, change the task rather than adding filler.

Wrong-answer feedback identifies the earliest likely reasoning break and gives a
small repair or recheck. Do not repeat the full solution for every distractor.
The correct explanation should derive the result and name its limiting condition.
Do not infer a diagnosis from one click or treat an immediate corrected retry as
independent success. A later fresh item can give better evidence; no retention
scheduler or mastery score is required.

Use prepared Exercises for proofs, coding/design reasoning or open construction
that deserves a rubric. Compare valid alternative reasoning fairly. Never label
ungraded prose correct or claim that Reviewed proves understanding.
